# Literature gap audit — 1 November 2026

This is a primary-source check for the manuscript's **raw-test PASS / bounded-oracle INSECURE** finding and its feedback-validity framing. The papers below are now integrated into the working manuscript and its author-year draft, and the PDF/DOCX files have been regenerated locally. Their rates must not be pooled with, or compared numerically to, the selected **21/45 post-onset submissions** in our older excluded C5 pilot. Those 45 submissions include repeated candidates (nine distinct SHA-256 values among the 21 discordant submissions), whereas the cited papers use different task, patch, or trajectory units.

## Strongest missing studies

1. **Zheng Yu, Wenxuan Shi, Xinqian Sun, Zheyun Feng, Meng Xu, and Xinyu Xing.** “Patch Validation in Automated Vulnerability Repair.” arXiv:2603.06858, 2026. [Primary paper](https://arxiv.org/abs/2603.06858); arXiv DOI [10.48550/arXiv.2603.06858](https://doi.org/10.48550/arXiv.2603.06858). The authors built PVBench with **209 cases from 20 projects** and evaluated three automated vulnerability repair systems. More than 40% of patches accepted by their basic tests failed added developer-derived `PoC+` tests. This directly supports the methodological point that a weak validation pass can overstate patch correctness. Their denominator is patches in real-project vulnerability cases, **not** repeated submissions from our synthetic finite tasks. Their added tests also capture developer intent and root-cause semantics that our bounded oracle does not establish.

2. **Tan Bui, Ting Zhang, Ferdian Thung, Yunpeng Xiong, Penghao Jiang, Xin Zhou, and David Lo.** “Vul4Py: Benchmarking Automated Vulnerability Repair in Python with Paired Exploit and Functional Oracles.” arXiv:2608.00692, 2026. [Primary paper](https://arxiv.org/abs/2608.00692); arXiv DOI [10.48550/arXiv.2608.00692](https://doi.org/10.48550/arXiv.2608.00692). Vul4Py packages **100 real Python vulnerabilities from 60 projects**, each with an exploit oracle and project-native functional tests. The paired oracle rejected **15 of 119 patches** that an exploit-only oracle would have accepted. This is a close design precedent for keeping two validation dimensions visible. Its detected failure is mainly a functional regression after exploit mitigation; our raw-test/oracle discordance concerns an authored bounded security property. Neither rate estimates the other.

## Closest verifier and feedback antecedents

3. **Tianyu Liu, Dingyuan Dai, Yufan Du, and Zhen Yang.** “From Dead Code and Static Requirements to Working Engines: Software Revival with Coding Agents.” arXiv:2609.36161, 2026. [Primary paper](https://arxiv.org/html/2609.36161v1). ReviveBench's construction audit reports **28 hidden-verifier defects**, including **24 false negatives** that rejected work judged correct. This is a direct precedent for auditing false rejections in a coding-agent benchmark. Our nine terminal disagreements are narrower: a finite family test passed and a separate hidden acceptance rule rejected the candidate. We have **not** independently established that those nine candidates were generally secure or should be counted as ReviveBench-style false negatives.

4. **Ziru Chen, Dongdong Chen, Ruinan Jin, Yingbin Liang, Yujia Xie, and Huan Sun.** “COBALT: Contextual Bandit Learning with Offline Trajectories for Multi-Turn Code Generation.” *Transactions on Machine Learning Research*, October 2026; [primary paper](https://arxiv.org/pdf/2602.03806). Their perturbation swaps expected outputs in public tests for 184 code-generation tasks and returns misleading failing tests during revisions. Models can abandon a correct program and lose hidden-test performance. Therefore our selected false-`FAIL` continuations are **not the first evidence** that wrong feedback can degrade code. COBALT manipulates test outputs in general coding tasks; our intervention is a false verdict after finite tests in authored security-repair tasks, while the paper's central claim concerns whether an unverified hidden veto permits a stopping-behavior inference.

The source check also narrowed our treatment of **Junjie Chen**'s [oracle-integrity audit](https://arxiv.org/html/2610.16067v2). Its state-changing reward computation corrupted a **separate post-run scorer**; the benchmark's own runner consumed the correct returned value and was unaffected. The working manuscript now states this boundary explicitly.

The manuscript's sampled citations to Sriram et al. [1], VRpilot [7], AgentAbstain [9], ReflecTool-Bench [15], SWE-Bench+ [23], PatchBench [24], and FixedBench [26] matched their linked primary pages on the claims checked. In particular, Sriram et al.'s paper specifies GCC, CodeQL, KLEE, and embedding-based retrieval; SWE-Bench+ reports both solution leakage and weak tests. The Chen [27] sentence was corrected as above. This spot check does not certify every reference or every sentence in the manuscript.
