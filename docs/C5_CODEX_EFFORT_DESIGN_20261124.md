# Does additional reasoning effort change a repair decision?

This design was written before dispatch on 24 November 2026. Its scope is every selectable model in the [native Codex CLI catalogue](c5_codex_catalog_20261124.json). Codex CLI 0.169.0 returned the ten names shown in the desktop picker and the additional selectable alias `gpt-daybreak-blue-latest`. Two hidden service aliases are outside the selection rule. Nine selectable models advertise six reasoning levels. Each Luna advertises five levels through `max`. This gives 64 available model–effort combinations in the catalogue. Access is measured separately for each attempted configuration.

## Two comparisons

1. **Sequential repair.** Repeat the [previous eight-episode task](C5_CLI_PILOT_20261124.md) for each of the eleven models at explicitly requested `low` and `high` effort. There are 176 episode slots. The model sees a four-entry table, its specification and a failure message. Half of the starts are correct and half have an error. The new check either repeats the failure or evaluates part of the specification. Report correct starts preserved, defective starts repaired, when each repair first succeeds, checks, redundant submissions, decision count and explicit stops. One decision consumes one CLI invocation. The cap is three. Match low and high on the same starting case and checker. The older default-effort observations remain a separate dataset.
2. **One-response panel.** Present the same batch of six deterministic functionality cases to each of the 64 supported configurations. The model submits one response covering the six cases. Correct and defective starting tables share the same public failure signal. Score the final answers against the finite specifications and distinguish preservation, repair and unnecessary rewriting. Six answers delivered together share context and are a single model invocation. A panel point compares one realized answer against one fixed batch.

## Resource accounting and interpretation

Record the requested model, explicit effort, reported usage and elapsed client time for observed decisions. Report output tokens and reasoning tokens separately when available. Reasoning tokens are a component of output where reported. Cached input tokens are a component of input. Durations include model service, queues and CLI startup. Concurrent client durations are unsuitable for estimating total elapsed batch time by simple addition. The study uses the existing ChatGPT login and cloud inference; no model weights run on the Mac. The two experiments together use up to three concurrent clients.

For quality, show numerator and observed denominator with planned coverage. Missing responses, inaccessible routes and unsupported settings retain separate statuses. For cost comparisons use the same metric and subset at both levels. If correctness ties, extra actions, time or tokens are still observable. A tie on six functions or eight trajectories does not establish a general model tie. Multiple CLI aliases can share unknown implementation details. A nominal effort requested in a CLI command is evidence of configuration, while provider attestation of deployed weights or internal compute is a different measurement. The tasks have no security endpoint.

Compare answer quality first, then compare the cost of obtaining equally good answers. One run per cell supplies no estimate of response variability.
