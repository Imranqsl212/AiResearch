# Can a coding assistant tell whether a failed check calls for an edit?

## Design fixed before collection

Five requested CLI configurations receive the same eight episodes. The Claude aliases are Opus, Haiku and Sonnet. The Codex requests are `gpt-6-sol` and `gpt-6-luna`. Each invocation uses a fresh context and the public decision history. Different products can supply different system instructions and may resolve aliases to changing deployments. Comparisons apply to the observed CLI configurations.

Each episode starts with the specification “double the input,” an explicit four-entry output table and a failed test message. Two matched pairs cover a correct starting table and a table with one incorrect entry. One defect lies inside the independent check’s coverage, the other outside it. Both pairs are evaluated with both available checkers. The correct table therefore recurs. A new check costs one decision. In one arm it repeats the failure. In the other it evaluates a subset of inputs. The agent may check, submit a replacement table or stop, with three decisions available. No model has access to the private reference.

For each configuration and checker, report the two correct starts preserved and the two defective starts repaired, with their respective observed denominators. Count explicit stops, checks, and rewrites on already correct starts. Check use measures exposure to the experimental change. If the agent never checks, success on that episode cannot be attributed to a new diagnostic. If everyone succeeds, the result establishes a ceiling on this known arithmetic task. Differences in unnecessary edits or decision use can still be described at that ceiling. A technical failure contributes an unavailable observation. Unattempted episodes stay visible. Report returned deployment metadata where available. There is one run per scheduled cell, no significance test and no ranking of general model capabilities.

These externally authored tables measure functionality. Security has no scored endpoint here. The separate verdict-by-budget experiment requires an agent to generate a correct starting solution before it receives the assigned verdict. The CLI exercise supplies no observations for that primary experiment.

The [task definition and scripted controls](C5_EVIDENCE_CHALLENGE.md) give the executable specification. The five configurations were selected at the authors’ request. The decision to use one transparent problem keeps the cost of checking instrument behavior low and limits what a positive result can establish.

**When did the fix happen?** In a post-hoc [step-by-step replay](../analysis/c5_cli_repair_timing_20261124.json), every initially defective table became correct on the first action. Three checks came after a successful repair, and one checked an initially correct table. All four occurred in episodes assigned the independent partial checker. The checker assignment was hidden until the first check returned. The difference in requests cannot be attributed to evidence the agent had yet to receive.
